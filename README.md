# LINCS-Dams
LINCS Dams is cost-effective prototype for small embankment dam monitoring. The experimental setup uses affordable sensors, including micro-electromechanical system (MEMS) in-place inclinometers (IPIs), water-level gauges, and vibration accelerometers. Sensor outputs are managed by a finite state machine (FSM) that defines accident driven alert and alarm levels while dynamically adjusting each sensor’s data sampling frequency, optimizing energy consumption and ensuring timely responses.

This repository contains the open-source code developed for this system, in addition to all the data gathered in experimental tests. The software developed builds upon previosly created code. The following sections go over the repository organization and the state of the art in dam monitoring.

## :file_folder: Repository Organization
The root of the repository has two folders: Documents and Code. On the Documents folder, you can find the experimental tests' results, in addition to a system installation and troubleshooting guide. The code folder has the software developed for each of the system's components, which includes the LiDAR module, the inclinometer and the state machine script.

### LiDAR Module
The folder */code/lidar/water_module* contains the evolution of this module's software. The last version, v3, is the final evolution of this software thus far. The system has fault-tolerance, instruction reception and low-pass filter features. Despite not having the full code available, this software was developed with the help of some code snippets that were made available by the system's creator, Figueiredo, on his Master's dissertation [document](http://hdl.handle.net/10362/165844). 
Parts of the LINCS Dams' architecture were also based on the work developed by Figueiredo, namely using a Raspberry Pi to run an MQTT broker and using a state machine to control behaviour. The LINCS Dams system further refined the state machine implementation approach by using a lightweight library and removing third-party services, adopting an on-premises architecture instead.

### IPI
The folder */code/ipi/ESP8266_wemosMini* contains the code for each of the three microcontroller types that compose this system. ESP0 is the microcontroller that is in each of the inclinometer's nodes. ESP1 and ESP2 are the two ESP8266 boards that comprise the master node of this subsystem. ESP1 is the bridge between ESP0 and ESP2, while ESP2 makes the connection between the IPI and the MQTT broker. The folder */code/ipi/tig-stack* contains the docker-compose yaml file and each of the services' configuration and support files.
The code that served as the foundation for this part of the LINCS Dams was developed by Santos and Marcelino (LNEC) and their work can be found [here](https://www.taylorfrancis.com/chapters/oa-edit/10.1201/9781003431749-419/development-laboratory-testing-low-cost-wireless-place-inclinometer-prototype-correia-dos-santos-marcelino). The IPI used for the LINCS Dams project is the same that was built by Santos and Marcelino, which enabled us to focus mostly on software development and test planning.

### State Machine Script
In */code/scripts/state_machine* there are the two versions developed for the dynamic behavior implementation based on a finite state machine, using the [Pytransitions](https://github.com/pytransitions/transitions) library. Please refer to the paper for a deeper explanation of the states, events, triggers, and overall logic behind the state machine's design.

### Test data (Dataset)
Each test is separated in test runs and each can be found on the Docs folder. The whole dataset, generated by the tests done for this project, in addition to previous tests made when the IPI was being built can be found in */code/ipi/tig-stack/telegraf/metrics.out*. This text file can be uploaded to Excel or you can use a Grafana instance to visualize the data.


## :books: State of the Art and Related Work

Santos and Marcelino put forward an [IPI prototype](https://www.taylorfrancis.com/chapters/oa-edit/10.1201/9781003431749-419/development-laboratory-testing-low-cost-wireless-place-inclinometer-prototype-correia-dos-santos-marcelino) that is not just a low-cost system but also innovates with collected data being transmitted wirelessly. This project’s main goal was to create an affordable IPI monitoring system that could reliably record embankments’ lateral deformations. The prototype successfully read inclination changes relatively accurately. Wireless communication between components was also 
effectively implemented.

Palma developed a [web application](http://hdl.handle.net/10362/183041) for real-time monitoring and visualization of data for In-Place Inclinometers (IPI), more specifically the IPI built by Santos and Marcelino. Efforts were made to create a modern and responsive design, which is a distinguishing factor, compared with most other comercial softwares for this purpose. Palma used up to date technologies such as ReactJS and Recharts to create meaningful visualizations, allowing users to make better decisions based on the data gathered by the IoT system.

Figueiredo, as part of his master’s [thesis](http://hdl.handle.net/10362/165844), designed a low-cost IoT system to measure the impact of docking ships on port infrastructures. The system was intended to collect, store, and analyze data, identify maintenance needs, and alert the relevant parties. The final prototype was able to reliably read the impact of vessels docking on a simulated port structure. 

Rohith et al. created a similar [test setup](https://ieeexplore.ieee.org/document/9243503) to the one used on this project, in addition to employing similar sensors to the ones used for this paper. They successfully tested the system in this scale dam replica setup, verifying the correct implementation of their smart dam monitoring system and the viability of this test apparatus.

Teixidó et al. created a [wireless system](https://www.mdpi.com/1424-8220/18/11/3817) that detected floods in smart homes.The goal was to develop a solution with which home owners could remotely interact with through the internet. The system’s behavior was implemented using a state machine and it was defined as the following cycle: the system hibernates to save energy, waking up periodically to send basic information or entering the alarm state if a flood was detected, in which case an alert message is sent to the user.

Ho et al., describe the theoretical implementation of an [autonomous home health care system](https://ieeexplore.ieee.org/document/5226920) to monitor the glucose levels of users, using a state machine to define the sensor's behaviour. The system would consist of an implantable sensor to measure the users’ glucose levels every minute, a base station and an external network of nodes installed in the user’s home. The implanted sensor would use a state machine to minimize the power consumption.

##  :computer: Software Infrastructure Installation Guide

This section goes over the software setup installation process to run the LINCS-Dams autonomous monitoring system.

###  Docker data storage stack

[Docker](https://www.docker.com/) is a platform that packages applications and their dependencies into lightweight containers, ensuring they run the same way in any environment. Containers start quickly, use minimal resources, and make it easy to develop, test, and deploy software consistently. In this project, Docker was used to deploy the data storage and visualization services.

Three applications were used to store and analyze the data collected by the system's various sensors: [InfluxDB](https://www.influxdata.com/), [Telegraf](https://www.influxdata.com/time-series-platform/telegraf/), and [Grafana](https://grafana.com/). All applications run in Docker containers and are managed together through two files, one from Docker-compose and another from configuration with several environment variables. To run these containers, you need to install Docker Desktop and run `docker-compose up -d` in the Docker-compose file directory(*code/ipi/tig-stack*). The *-d* flags makes the docker compose tool to run detached, allowing you to keep using the same terminal window. If you don't have the images installed yet, they'll be transferred and the containers will start automatically.

The configuration files uploaded on this repository have been redacted from personal or identifiable variables. All the fields you should update are marked with a `CHANGE ME` comment. As such, please set up your informations on the following files:

* Environment variables' file (*code/ipi/tig-stack/.env*)
    *  Set InfluxDB's username and password (lines 8 and 9)
    *  Set InfluxDB's organization and bucket names (lines 15 and 16)
*  Telegraf's configuration file (*code/ipi/tig-stack/telegraf/telegraf.conf*)
    * On section *[[outputs.influxdb_v2]]*, the environment file previously mentioned is used to set some values. If you are using the file, and have already updated it, no need to change anything here. If you are hardcoding your variables, add the following InfluxDB's informations:
        *   Line 1005 - host name
        *   Line 1008 - admin token
        *   Line 1011 - organization
        *   Line 1014 - bucket
    * On section *[[inputs.mqtt_consumer]]*, change the following lines (Note that there are two identical blocks for this input origin, one for each sensor):
        * Lines 8639/8656 - Raspberry Pi's IP address. You can save more that one address, which is handy if you don't always use the same Wi-Fi. If you are unsure about your RPi's address, SSH into it and run `hostname -I`
        * Lines 8642+8643/8659+8660 - MQTT broker's username and password.
        * You can also change other configuration aspects of this input section, but these are the ones you must update before you start using the system. Feel free to go through [Telegraf's documentation](https://docs.influxdata.com/telegraf/v1/configuration/) to explore these other options.
     
In the event of the original Docker-compose file is no longer available, or if you wish to create your own custom container stack, the following were the images and versions used for this project. The links for these images also contain useful information to correctly setup the containers, configuration-wise.

* [influxdb:2.7.4](https://hub.docker.com/_/influxdb)
* [telegraf:1.27.4](https://hub.docker.com/_/telegraf)
* [grafana/grafana-oss:10.1.0](https://hub.docker.com/r/grafana/grafana)

Finally, using a Docker volume, at least for the InfluxDB container, is recommended to ensure the data you gather using the monitoring system persists on your computer. The metrics.out file (telegraf's output file) also keeps a record of all the data sent to the broker. To share your data, follow these steps:

1. Backup Influx's container data by running `docker exec -e INFLUX_TOKEN=<ADMIN_TOKEN> -t influxdb influx backup /backup`. This creates a full backup of everything. If you only want to share a single bucket run `docker exec -e INFLUX_TOKEN=<ADMIN_TOKEN> -t influxdb influx backup --org <ORG> --bucket <BUCKET> /backup`. These commands create backups **inside** the container, not on your machine!
2. Copy the backup from the container the host (i.e. your computer) with `docker cp influxdb:/backup ./influx_backup`. Now you've extracted the data from the container's environment to your computer's file system.
3. Zip the ./influx_backup folder and send it to the receiver(s)

The data gathered during and between the tests for the LINCS Dams system is available on this repository on *documents/InfluxDB_data_mount.zip*. To mount this or any other existing data on a new InfluxDB instance (i.e. you are mounting existing data on a new InfluxDB container or another machine), do as follows:

1. Make sure this second InfluxDB instance is running on the same or a newer version and the user has an admin token (if you shared everything) or a scoped token (if you shared specific buckets)
2. Mount the folder on a container with `docker cp .\influx_backup <new_influx_container>:/backup`. This simply transfers the folder from your computer's file system to the container's. For the container to "see" the changes you must restore it. See which of the next points matches your scenario and proceed accordingly:
    1. If you are mounting the data on a fresh new InfluxDB container run `docker exec -e INFLUX_TOKEN=<ADMIN_TOKEN> -t <influx_container> influx restore /backup`. This overwrites server data, use it if you want an "as-is" restoration of the original container. Do **not** go for this option if you do not wish to use a fresh server.
    2. If you are mounting **a bucket**, not a full InfluxDB instance, and want to create a new bucket to store the data you received run `docker exec -e INFLUX_TOKEN=<ADMIN_TOKEN> -t <influx_container> influx restore --org <ORG> --bucket <SOURCE_BUCKET_NAME_IN_BACKUP> --new-bucket <NEW_BUCKET_NAME> /backup`. This creates a new bucket on the go, so you don't have to worry about previously creating the bucket. If you are mounting a bucket, this is probably the best way to do it.
    3. If you are mounting **a bucket**, not a full InfluxDB instance, and want to mount it on an existing bucket within your InfluxDB container `docker exec -e INFLUX_TOKEN=<ADMIN_TOKEN> -t <influx_container> influx restore --org <ORG> --bucket <TARGET_BUCKET> /backup`. The names of the buckets must match!!! Go for this option if you already have an InfluxDB instance running on Docker, and want to store the new data you received together with your other data. This is the same as the previous option, but you have to create the bucket beforehand, and make sure the names match (should be easier to go for option 2).

To verify if the container is working run `docker exec -e INFLUX_TOKEN=<ADMIN_TOKEN> <influx_container> influx bucket list --org <ORG>` to list all buckets in the organization. You should spot the new bucket if everything went right. Optionally, you can also query data from the new bucket with `docker exec -e INFLUX_TOKEN=<ADMIN_TOKEN> <influx_container> influx query 'from(bucket:"<TARGET_BUCKET>") |> range(start: 2025-08-06T08:00:00+01:00, stop: 2025-08-06T11:00:00+01:00) |> limit(n:5)'`. It should return the first five entries on the database stored during a testing day.

### Raspberry Pi and Mosquitto broker

A Raspberry Pi 5 (4GB RAM model) was used to run the MQTT broker, making it a key component in communication between devices in this system. As such, it is necessary to install an operating system on the RPi, as well as install and register the broker as a service on the board's operating system. To learn more about the Raspberry Pi is and how it works, visit the following [link](https://randomnerdtutorials.com/getting-started-with-raspberry-pi/).

#### Required Components

By default, the Raspberry Pi comes without internal memory or an operating system. Therefore, if the device is new, it is also necessary to obtain a microSD card and, possibly, a reader for cards of this format. For the model 5, it is recommended to use the power supply of the same brand for this family of boards. These following items are required to set up the LINCS-Dams monitoring system:

* [Raspberry Pi 5](https://www.raspberrypi.com/products/raspberry-pi-5/)
* [Official Raspberry Pi 5 power supply](https://www.raspberrypi.com/products/27w-power-supply/?variant=27w-power-supply-eu-white)
* MicroSD card (any card that is 16GB or higher is fine, for this project we used a 32GB card)
* MicroSD card reader (check if your machine already has this port)

-> These were the items used for this project, you can opt for different components and still achieve the same communication infrastructure.

Other optional items include:

* Micro HDMI to HDMI cable, if you wish to use the Raspberry Pi with a monitor. This can be handy, specifically in the first setting up stages, however the Pi can run headless (no graphical interface);
* [Bumper](https://www.raspberrypi.com/products/bumper/) or case (if its has a fan system can help with performance);
* Performance and cooling systems, ranging from small heatsinks to active cooling systems.

#### Raspberry Pi Configuration (Wi-Fi and SSH)

Once you have gathered the necessary materials, you have to complete the following tasks to prepare the RPi: (i) Install an operating system, (ii) configure the device, and (iii) install and register the Mosquitto Broker.

This [guide](https://randomnerdtutorials.com/installing-raspbian-lite-enabling-and-connecting-with-ssh/) goes over the first two tasks. 

In this project, Raspberry Pi OS (recommended option in Raspberry Pi Imager) was used. It is possible to install other OS, namely popular Linux distributions or other versions of the recommended RPi OS. If you intend to use the RPi graphical interface, it is recommended to install the RPi OS recommended by the application. There are other lighter versions, however these may not support the use of displays. 
When customizing the OS settings, consider whether the RPi will be connected to networks where there are no other devices with the default hostname. If the RPi is used in spaces such as colleges, laboratories, etc., changing the hostname in the Imager application is recommended, as there may be another device with the same hostname connected to the network. It is possible to change this name later, but the task is simpler using the graphical interface of this application.

When installing the OS on the microSD card, proceed with caution and verify that the operating system will be loaded onto the correct memory unit (microSD card). The RPi Imager application will delete everything stored on the selected memory unit and leave only the OS.

The guide suggests installing putty to test the connection to the board via SSH from an external device such as a computer. During the development of the project, the board was accessed directly from the Windows machine terminal with the command `ssh username@hostname`. If both devices are on the same network, the next prompt will ask for the password for this user. Both the hostname and the name and password must be defined in RPI Imager. In case of error, confirm that both the computer and the Raspberry Pi are connected to the same network. Connecting the RPi to a monitor makes it easier to solve this type of problem, allowing you to check if the board is actually connected to the network and, if not, connect it to Wi-Fi manually.

#### Mosquitto MQTT Broker Installation

See this [guide (randomnerdtutorials)](https://randomnerdtutorials.com/what-is-mqtt-and-how-it-works/) to find out more about the MQTT communication protocol. Follow this [guide (randomnerdtutorials)](https://randomnerdtutorials.com/how-to-install-mosquitto-broker-on-raspberry-pi/) to install the Mosquitto broker on the Raspberry Pi. Finally, confirm that the broker is working correctly as instructed in this [tutorial (randomnertutorials)](https://randomnerdtutorials.com/testing-mosquitto-broker-and-client-on-raspbbery-pi/).(Links last visited on 10/08/2025).

To register the broker as a service, enabling it to run automatically when the Raspberry Pi boots, run the following commands in the terminal:

```shell

sudo systemctl start mosquitto

sudo systemctl enable mosquitto

sudo systemctl restart mosquitto

```

To confirm that Mosquitto is running as a service run `sudo systemctl status mosquitto`. If everything is running correctly, the output should contain the following section:

```shell

Loaded: loaded (/lib/systemd/system/mosquitto.service; enabled)
Active: **active** (running) since ...

```

If you identify that section on the output, the service is enabled and running. At this point, the communication component of the LINCS-Dams system is effectively running.
